# 云原生软件技术 Lab 2：场地预约系统
# Kubernetes 工作负载编排

## 一、实验主题

在 Lab 1 场地预约系统的基础上，使用 Kubernetes 部署并编排应用。各小组需要结合系统中不同组件的运行特征，自主选择合适的 Kubernetes 工作负载与资源配置，并基于新功能，实践 Job、CronJob、DaemonSet 等工作负载。

本实验是课程三阶段项目的第二阶段。各小组应在保留 Lab 1 功能和容器化成果的基础上继续开发，并保留完整、可复现的代码仓库和部署配置。

## 二、实验目标

完成本实验后，学生应能够：

1. 创建并使用 Kubernetes 实验环境；
2. 将已有容器化系统部署到 Kubernetes；
3. 根据组件是否无状态、是否需要稳定身份或持久化存储、是否持续运行或一次性执行等特征，选择合适的工作负载；
4. 理解并使用 Deployment、StatefulSet、Job、CronJob、DaemonSet、Service、ConfigMap、Secret 和 PersistentVolumeClaim（PVC）等资源；
5. 使用 Service 为需要被访问的组件提供稳定的服务发现或访问入口；
6. 根据实际负载、状态特征和访问方式，自主设计副本数与副本扩展方案；
7. 完成工作负载运行、一次性任务、定时任务等。

## 三、组织方式与通用要求

- 以小组为单位完成，沿用 Lab 1 的项目仓库；
- 可以使用生成式 AI 辅助分析、编码、配置和排错，但小组成员必须能够解释、修改和验证最终提交内容；
- 配置必须从代码和镜像中分离。不得提交真实密码、Token、访问密钥等敏感信息。

# 第一部分：Lab 2 实践要求

## 一、准备 Kubernetes 实验环境

各小组应自行准备可运行 Kubernetes 的实验环境。可使用本地单节点集群或课程提供的集群，例如：

- minikube；
- Docker Desktop 内置 Kubernetes；
- kind。

实验报告应记录实际使用的 Kubernetes 环境、版本、节点数量和镜像使用方式。

## 二、保留并迁移 Lab 1 系统

Lab 2必须保留 Lab 1 的基本业务功能，并将已有系统从 Docker Compose 迁移到 Kubernetes。系统至少应继续支持：

1. 查询场地列表和场地详情；
2. 创建场地；
3. 创建预约并检查时间冲突；
4. 查询预约记录；
5. 取消预约。

各小组应梳理前端、API、数据库及其他已有组件的运行特征，并使用适当的 Kubernetes 资源进行部署。设计时至少需要考虑：

- 哪些组件需要持续提供服务；
- 哪些组件是无状态的，适合通过多个副本扩展；
- 哪些组件需要稳定身份、稳定存储或有状态管理；
- 哪些组件需要通过 Service 被其他组件或用户访问；
- 哪些组件不应暴露 Service；
- 是否需要并如何使用 PVC 保存持久化数据。

要求在 Kubernetes 配置中实际使用并说明 Deployment 和 StatefulSet。具体由哪个组件使用哪种工作负载，由各小组根据上述需求自行决定，并在报告中说明理由。

## 三、Kubernetes 服务、配置和存储要求

### 3.1 Service 与访问方式

对需要被集群内其他组件访问的服务，应创建合适的 Service。各小组自行决定 Service 类型和是否需要对集群外暴露访问入口，但应满足：

- 前端或测试客户端能够访问业务 API；
- 业务 API 能够访问其依赖的服务，例如数据库、缓存或消息组件；
- 组件间访问应使用 Service 名称、DNS 名称或其他稳定入口，不得依赖临时 Pod IP；
- 不应为了方便而无必要地将数据库等内部服务端口暴露到集群外。

### 3.2 配置外部化

- 至少使用一个 ConfigMap 保存非敏感配置，例如服务地址、端口、运行环境或任务参数；
- 至少使用一个 Secret 保存敏感配置，例如数据库账号或密码；
- 应用应通过环境变量、文件挂载或其他合理方式读取配置。

### 3.3 持久化存储

对需要在 Pod 重建后保留的数据，应使用 PVC 或课程环境中等价的持久化机制。各小组应说明：

- 哪些数据需要持久化；
- 使用的 StorageClass、PVC 或等价存储配置；
- 数据库或其他有状态组件如何挂载和使用存储。

### 3.4 副本数与Service设计

对于需要持续提供服务的无状态组件，各小组可考虑访问压力、故障影响、资源限制和应用是否共享状态等因素，自主决定是否设置多个副本以及具体数量。

实验至少应满足以下要求：

1. 选择一个适合水平扩展的服务，设置多个 Pod 副本；
2. 为该服务配置合适的 Service 或说明等价的稳定访问方式；
3. 通过连续请求、日志、响应中的实例标识或其他证据，证明请求可以被多个副本处理；
4. 说明该组件的副本数选择依据，以及为什么其他组件不一定适合使用相同副本策略。

## 四、Kubernetes 工作负载实践任务

除第二部分要求的 Deployment 和 StatefulSet 外，各小组还可按照以下需求完成 Job、CronJob、DaemonSet 的实践，并说明设计理由。

### 4.1 一次性报告任务：Job

新增“场地利用率报告”能力。报告至少统计指定时间范围内：

- 各场地预约次数；
- 各场地累计预约时长。

将一次性生成报告的处理过程设计为 Kubernetes Job。Job 应能读取必要配置和预约数据，生成并保存报告结果。各组可自行选择报告触发方式，例如通过 API 创建任务记录后触发、由脚本创建 Job，或采用其他合理方案。

报告任务至少应具有可查询或可追踪的唯一标识，例如 jobId、Kubernetes Job 名称或两者的关联。应记录任务的开始、成功或失败状态，并将必要结果保存到可查询位置。

### 4.2 定时报告任务：CronJob

基于同一报告逻辑或其他合理的统计逻辑，创建一个 Kubernetes CronJob。CronJob 应按组内设定的调度周期自动执行，并生成可验证的结果。

实验时可以使用便于观察的短周期；报告中应说明生产环境建议的周期，以及如何避免任务重叠、重复写入或并发冲突。

### 4.3 节点级任务：DaemonSet

设计并部署一个 Kubernetes DaemonSet，以满足“每个节点都需要运行一个副本”的场景。具体功能由各小组设计，建议与系统运行、运维或观测有关。可选方向包括：采集节点或容器日志、收集节点级运行信息、执行节点级检查、提供节点侧代理能力等。无需为了使用 DaemonSet 而改变核心预约业务逻辑。应验证 DaemonSet 在当前集群每个符合条件的节点上创建了对应 Pod。
